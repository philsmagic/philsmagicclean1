AEO Before / After Report · v1 (preview build)

Can answer engines read philsmagicclean.com?

Prepared for E.L. · 5 October 2026 · Bristle, for Sable · Before = live site; After = review build (PR #1), not yet launched

Same website to a person. A different website to a machine.

The live site is a single-page React app: every URL, including robots.txt and made-up paths, returned the same empty shell with one <div> and 369 KB of JavaScript. Crawlers that don't run JavaScript — most answer engines — saw nothing. The rebuild serves every page as finished HTML with headings, text, links and a schema label block. The design changed only to adopt Phil's logo colours and fonts; the copy is carried word for word.

The part that matters: what a crawler actually receives

Both panels are the real response for the home page, fetched with curl and no JavaScript — exactly what a crawler receives. Nothing is edited. The before is the entire visible body; the after is the first part of a page that goes on for 6,000 characters.

Why the UI doesn't decide this
A visitor's browser assembles the before page in a split second, so it looked fine. An answer engine reads what arrives and moves on. If the headings, the answer and the labels aren't in that first response, the page does not exist to it — however good it looks.

What people see — nearly the same page

Home page, desktop, full-page capture. Layout and copy are the same; the after adopts the logo's blue, Archivo headings, a visible table of contents, and keeps teal for the one action button.

What changed in the build

  • Rendering: React single-page app → Astro static site. Every route is a complete HTML file at build time.
  • Structure on every page: one H1, a one-paragraph answer under it, ids on section headings, a table of contents, visible breadcrumbs, plain links, hub ↔ spoke links both ways.
  • Schema: one JSON-LD graph per page with stable @ids — LocalBusiness, Person (Phil), WebSite, WebPage, plus BreadcrumbList, Service, BlogPosting, FAQPage where the content is visible.
  • Crawl hygiene: robots.txt, sitemap, real 404s, 301s for /new and /update, one canonical per page, snippet-friendly robots directive.
  • Live defects fixed: titles and descriptions on /about, /contact, /reviews; the three body-less blog posts no longer link to 404s; /new no longer duplicates the home page.
  • Measurement preserved: Meta pixel PageView on every page load; Lead event on Jobber-form clicks, tagged janitorial vs general, same ids.
  • Brand: logo-sampled blue palette, Archivo headings, Source Sans 3 body; teal kept for the one action button. Copy carried word for word.
  • Measurement added: GA4 `phone_tap` on every tel: click and `quote_click` on every Jobber-form click (both site-fired key events, registered by name in GA4 Admin, request_type matches the Meta Lead tagging); same GA4 measurement ID as before; Meta pixel PageView per page load + Lead on Jobber clicks unchanged.

What this teaches

  • AEO is decided by what arrives in the first response, not by what the page becomes after JavaScript runs.
  • A site can score well on hosting (HTTPS, compression, caching) and still be invisible — most of the before's 31% came from Netlify, not the site.
  • Labels (schema) only count when they sit in that first response and match the visible words exactly. Adding schema to the old site would have changed nothing.
  • Define each entity once with a permanent ID and point to it everywhere; that's how a machine learns the business on the blog and the business on the reviews page are the same business.
  • The links to Phil's other profiles (sameAs) are the single highest-value input still missing — they connect the website to the 42 reviews.
  • What the rebuild does NOT fix: Phil's absence from Google's local pack for generic searches. The local pack is driven by the Business Profile (category, service area, reviews), not the website — that is the separate GBP correction pass. The site controls crawlability, structured data, answerability and page experience; the report claims only those.
